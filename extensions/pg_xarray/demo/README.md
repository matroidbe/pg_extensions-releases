# pg_xarray Demo Book

A runnable tour of pg_xarray — five chapters that take you from "I have
some scientific files" to "my Postgres is a feature store for ML." Each
chapter is one self-contained `.sql` file you can paste into `psql`,
DBeaver, pgAdmin, SQLBook, or any other SQL client.

Two extra views of the same book are generated by
`build_notebook.py` — pick whichever your editor likes:

* **[`demo.sqlbook`](demo.sqlbook)** — VS Code [SQL Notebook] extension
  format. Plain-text with `-- SQLBook: Code` / `-- SQLBook: Markdown`
  cell markers. The extension picks the Postgres connection from its
  UI; no Python kernel needed. Run cells with the inline "▶" buttons.
* **[`pg_xarray_demo.ipynb`](pg_xarray_demo.ipynb)** — Jupyter notebook
  (VS Code, JupyterLab, Colab, etc). Renders out of the box; to
  *execute* cells in-place, install [jupysql] (`pip install jupysql
  sqlalchemy psycopg2-binary`) and run the setup cell.

Both formats are auto-generated from the `.sql` files — edit a chapter,
re-run `python3 build_notebook.py`, and both books refresh.

[SQL Notebook]: https://marketplace.visualstudio.com/items?itemName=cmoog.sqlnotebook
[jupysql]: https://jupysql.ploomber.io/

## Pre-requisites

* PostgreSQL 14-18 with **PostGIS** installed (`CREATE EXTENSION postgis`).
* `pg_xarray` installed with the readers you want:
  ```
  cargo pgrx install --features "reader-netcdf reader-grib"
  ```
  See [extensions/pg_xarray/test.sh](../test.sh) for the exact env vars
  required for the NetCDF system-library build (libnetcdf-dev,
  libhdf5-dev, PKG_CONFIG_PATH).
* The demo fixtures are committed under [`fixtures/`](fixtures/) — Zarr v3
  store + NetCDF + GRIB2 + SELAFIN, ~20 KB total. No fixture-build step.
  To regenerate from scratch (e.g. after changing `make_fixture.py`),
  run `/usr/bin/python3 ../tests/make_fixture.py demo/fixtures && rm -rf demo/fixtures/sim`
  from the extension root.

## Quick start

The chapter SQL files hardcode the absolute fixture path
`/home/ubuntu/dev/pg_extensions/extensions/pg_xarray/demo/fixtures`. If
your checkout lives elsewhere, search-and-replace that path before running.

```bash
psql -h localhost -d mydb \
  -f 00_setup.sql \
  -f 01_register_local.sql \
  -f 02_cloud_native.sql \
  -f 03_fdw_and_joins.sql \
  -f 04_feature_views.sql \
  -f 05_unstructured_mesh.sql
```

…or run them one at a time, reading the narration as you go.

## What's a catalog?

pg_xarray treats a scientific file (Zarr store, NetCDF, GRIB2,
SELAFIN) as an **index** rather than a copy. `pgx.register_file` walks
the file once and writes:

* `pgx.datasets` — what dataset this is
* `pgx.variables` — variables with CF metadata (units, standard_name,
  scale_factor / add_offset / fill_value)
* `pgx.chunks` — one row per chunk / message / timestep, with:
  * `bbox_envelope` (PostGIS, GIST-indexed) — for "around this station"
  * `time_range` (TSTZRANGE, GIST-indexed) — for "during this window"
  * `level_range` (NUMRANGE) — for "at this altitude / pressure"
  * `uri`, `byte_offset`, `byte_length` — where the bytes are

`pgx.fetch` (and friends) take WHERE-like predicates, prune candidate
chunks via the catalog indexes, then **range-read just the matching
bytes** via OpenDAL — same code path for `fs://`, `https://`, `s3://`,
`gs://`, `azblob://`. A 100 GB ERA5 file with a "Brussels, last 24 h"
query becomes ~tens of MB-scale range GETs.

The FDW (`CREATE FOREIGN TABLE … SERVER pgx_fdw OPTIONS (dataset
'era5', variable 't2m')`) wraps a `(dataset, variable)` pair in a
regular-table façade. WHERE-clause and JOIN clauses on `lat`/`lon`/
`level`/`time` push into the FDW as bbox + time + level predicates
(both static constants and runtime parameters from outer-row joins).

## What's a mesh?

Unstructured-grid scientific data — TELEMAC's hydraulic simulations,
FEM stress analyses, particle clouds — doesn't fit a regular lat/lon
grid. pg_xarray stores:

* `pgx.meshes` — one per dataset
* `pgx.mesh_versions` — for deforming meshes
* `pgx.mesh_nodes` — vertices with PostGIS `geom`
* `pgx.mesh_cells` — triangles / polygons with `node_ids[]` + centroid

`pgx.fetch_mesh(dataset, variable, ...)` returns
`(node_id, cell_id, geom_wkt, time, value)` — the catalog joins the
chunk values to the mesh geometry so spatial queries work the same
as for regular grids.
